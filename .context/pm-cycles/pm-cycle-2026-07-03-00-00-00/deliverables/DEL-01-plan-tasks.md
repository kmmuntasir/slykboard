## Parallelization Strategy

Tasks are grouped into batches by dependency order. Run batches sequentially;
within a batch, conflict-free tasks run in parallel.

### Batch / Dependency Diagram
```
Batch 1 (parallel — disjoint files):
  [T1 frontend deps]   [T2 backend sanitize parity]   [T3 frontend sanitize parity]
                \                       |   (allow-list must match T2 byte-for-byte;
                 \                      |    disjoint files, no merge conflict)
                  \                     |
                   v                    v
Batch 2:                                [T4 toolbar rewrite + extensions + handlers]
                     (T4 depends on T1 only; can run parallel with T2, T3)
```

### Merge-order rules
1. **T1, T2, T3 are mutually file-disjoint** (`frontend/package.json`+`frontend/pnpm-lock.yaml` / `backend/*` / `frontend` src sanitize + `DescriptionField`) → merge in any order, no conflicts.
2. **T4 touches `frontend/src/components/RichTextEditor.tsx` only** → no overlap with T3 (which never edits `RichTextEditor`) or T1 (which never edits source). **Merge T4 after T1.**
3. **CRITICAL — T3's allow-list MUST be byte-for-byte identical to T2's backend allow-list** (the plan's canonical list, Change 6). Verify parity before merging; the two tasks edit disjoint files so this is a **spec check**, not a merge conflict.
4. **Do NOT edit the shared `frontend/src/components/ui/ToggleGroup.tsx` primitive** in any task. T4 scopes `flex-wrap` to the consumer `className` override specifically to avoid regressing `ThemeToggle.tsx`.
